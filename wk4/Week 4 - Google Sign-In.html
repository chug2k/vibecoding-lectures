The idea · Authentication

Authentication is how an app learns — and can trust — who's using it.
Every private or personal thing software does is built on that one answer.

Ownership

Things can be yours.

Your tasks, your drafts, your settings — data tied to your account, invisible to everyone else.

Permissions

Rules about who sees what.

Once the app knows who you are, it can decide what you may see and do. That's the foundation for everything we build next.

Accountability

Actions have names on them.

Who created this? Who changed that? With real users, the app can answer.

The approach · Why Google

We could build our own username-and-password system.
Almost nobody should.

The liability

Passwords are a security job.

Storing them safely, resets, phishing, breaches — get one detail wrong and you've leaked everyone's password.

The shortcut

Google already solved it.

World-class security, two-factor, breach detection — and every Anduin person already has the account.

The bonus

It can lock to Anduin.

One setting tells Google to refuse anyone outside anduintransact.com — before they ever reach your app.

Concept · The moving parts

Five values that must match.

Everything you'll do today is connecting these five. When something breaks, it's almost always one of them not matching.

PieceLives inWhat it's for
User type Google Internal = only your Workspace can sign in. This is the lever that locks the app to Anduin.
Callback URL Supabase Where Google sends the user back: https://<ref>.supabase.co/auth/v1/callback
Client ID Google → Supabase Public identifier for your app. Fine to be seen.
Client Secret Google → Supabase Private proof the request is really from your app. Shown once.
Redirect URI Google Allow-list of return addresses. Must contain the callback URL byte-for-byte.

Module 1 · Supabase

Enable Google. Copy the callback.

Authentication → Sign In / Providers → Google, toggle Enable Sign in with Google on. Leave the ID + Secret fields empty for now.
At the bottom of the panel, hit Copy on the Callback URL — and leave this tab open.
Don't retype
Use the Copy button. This value has to match byte-for-byte in Google later — a stray character here is the #1 failure of the day.

Module 2 · Google Cloud

Create a project — under the org.

Open console.cloud.google.com signed in with your work account.

Module 2 · Google Cloud

Set the audience to Internal.

The consent screen wizard has four short parts. This radio button is the whole org restriction — everything else is filling in names and emails.

Google Auth Platform → Get started. App name + support email. The name can't contain “Google” — it gets rejected.
Audience → Internal: “Only available to users within your organization.”
Contact info, agree, Create. Done — no test users, no verification review.

Audience → Internal. External is for public apps — not today.

Module 2 · Google Cloud

Create the OAuth client.

Clients → Create client, application type Web application.
Authorized JavaScript origin: http://localhost:3000 — where your app runs.
Authorized redirect URI: paste the Supabase callback from Module 1. Exactly as copied.
The fumble step
The redirect URI must match the callback byte-for-byte — even a trailing slash earns you redirect_uri_mismatch. Paste, don't type.

Redirect URI = the Supabase callback URL, pasted

Module 2 · Google Cloud

Copy both credentials.

Click Create. A dialog shows your Client ID and Client Secret.
Copy both — or hit Download JSON. They go into Supabase next.
Shown once
Close the dialog and Google never shows the secret again. If you lose it, you don't hunt for it — open the client and generate a new one.
Notice
The dialog itself says it: “OAuth access is restricted to users within your organization.” Internal is doing its job.

Module 3 · Back in Supabase

Paste them into Supabase.

Back in the Google provider panel: Client ID into Client IDs, Secret into Client Secret → Save.
Authentication → URL Configuration: Site URL http://localhost:3000.
Add a Redirect URL of http://localhost:3000/**.
Why the **
The wildcard lets Supabase send users back to any page of your app — /dashboard, not just the front door.

Supabase → Authentication → URL Configuration

Module 4 · Your code

Then: one line of code.

app.js — the sign-in button 
await supabase.auth.signInWithOAuth({
  provider: 'google',
  options: {
    redirectTo: window.location.origin,
    queryParams: { hd: 'anduintransact.com' },
  },
})
Everything before this was configuration. Wire this call to your “Sign in with Google” button — Supabase builds the Google URL and runs the whole dance for you.
hd just filters the account chooser to Anduin accounts. It's a courtesy, not the lock.
The lock is Internal — the radio button from Module 2. Google enforces it server-side, no matter what the user does.

Module 4 · The proof

Verify it works.

Click the button — the Google account chooser appears, showing your @anduintransact.com account.
Pick it — you land back in your app, signed in.
A new user appears under Supabase → Authentication → Users, and auth.getUser() returns them.
The fourth check · do this one

Now try a personal Gmail.

Google blocks it with an authorization error before it ever reaches your app. That error is not a bug — it's the whole point of today. If an outsider gets through, something's wrong.

Debugging · Leave this slide up

When it breaks: check the match.

Every error below is one of the five values not matching. The symptom points straight at which one.

What you seeWhich valueFix
redirect_uri_mismatch Redirect URI Re-copy the callback from Supabase, re-paste into Google. Watch for a trailing slash.
“Internal” isn't offered User type Your GCP project isn't under the org — wrong Google account. Recreate it signed in with work.
invalid client / secret Client ID + Secret Re-paste both into Supabase. Lost the secret? Generate a new one in Google.
signs in, bounces to wrong page Supabase URLs Set Site URL and add http://localhost:3000/** in URL Configuration.
