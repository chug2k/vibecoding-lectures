The mechanics

The mechanics

Git is really five verbs

commit
Save a checkpoint of your work. Local, and yours until you push.
branch
Start a separate line of work without disturbing main.
push
Send your commits up to GitHub for everyone else.
pull
Bring everyone else's commits down to you.
merge / rebase
Fold a branch back together with another.
Five verbs cover about ninety percent of it.05

The mechanics

Commits, branches, and copies

A commit is a snapshot. A branch is a line of work. And every clone holds the whole thing.

Both copies hold the entire history — no central server. “Decentralized” just means GitHub is the copy everyone agrees to meet at, so push and pull simply sync the two.

Each clone is a full copy — that's why push and pull exist.06

Bringing branches back together

Merge vs rebase

Two ways to fold a branch back in. Same destination, different-looking history.

Merge

Tie two branches together and keep the full history — sometimes with a merge commit.

Rebase

Replay your commits on top of the latest base, for a cleaner, linear history. Usually nicer for short-lived branches.

Know the words — and let the tool run it.

Aside

Why we prefer rebase

One of these sparks joy.

A clean fast-forward pull on top; the same pull as a wall of merge conflicts on the bottom. Rebasing onto the latest main keeps history tidy and linear — so day to day, it looks a lot more like the top.

Best practices

If you remember nothing else

Three rules that keep you out of trouble

1
Always branch off main.
Pull the latest main first, then start your branch from it.
2
Don't branch off another branch.
Keep every branch rooted in main — no stacking branches on branches.
3
Open a PR — and rebase to merge it back.
When merging into main, choose rebase for a clean, linear history.

Heavily simplified, but enough to work safely — drop it in an AGENTS.md so your agent follows it too.

And avoid --force. Almost everything in Git is undoable once it's committed — a force-push is the main way to lose work for good, including other people's. Be sure you truly need it before you (or your agent) reach for it.
Simple enough to remember; good enough to ship.12

A cautionary tale

A cautionary tale

This, but with your team's history

git push --force is the stick-in-your-own-spokes of version control. Almost nothing else in Git can do this much damage — be very sure before you reach for it.

Before you request review

  • Does this PR do one thing?
  • Any unrelated AI edits in the diff?
  • Can someone understand it from the diff alone?
  • Is the target branch correct?
Branches aren't only for PRs. Want to compare two versions or test a risky idea? Keep it on a branch and switch back and forth. You won't run git switch yourself — just tell Claude Code: “try this in a branch so I can switch between them.”

Best practices

Branch strategy

Dev / staging / main

main

Production-ready source of truth. The branch the world runs on.

staging

Pre-production. Where you test and integrate before release.

dev

The active integration branch where work comes together.

Small teams PR straight to main. Cautious teams run dev → staging → main. Match the ceremony to the risk.

Housekeeping

A detail worth knowing

.gitignore — files Git pretends it can't see

Generated junk, caches, local config, and logs — kept out of shared history.

# .gitignore
node_modules/
*.tmp
.env
dist/
Not a fix for a secret you already committed. A committed API key is still in history — that's a different problem with a different fix.
